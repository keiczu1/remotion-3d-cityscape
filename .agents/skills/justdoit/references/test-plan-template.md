# Шаблон Тест-Плана

Используй этот файл как базовую форму для `test-plan.md`, только если задаче действительно нужен отдельный контракт проверок.

## Когда Нужен

- исправление бага;
- изменение поведения;
- рискованная интеграция;
- важный пользовательский сценарий;
- сложная приемка, которую легко упустить в одном только плане.

## Принципы

- Привязывай покрытие к реальным изменениям поведения из плана.
- Предпочитай запускаемые проверки, а не расплывчатые намерения.
- Не копируй набор `lint/typecheck/test/build`, если он не соответствует репозиторию.
- Оставляй только те секции, которые реально нужны этой задаче.

## Рекомендуемый Каркас

````md
# Test Plan

## Источник
- Задача: <краткая формулировка задачи>
- Файл плана: <path>
- Файл статуса: <path или N/A>
- Обновлено: <YYYY-MM-DD>

## Что Проверяем
- Внутри: <поведения, сценарии, компоненты, API>
- Вне проверки: <что сознательно не покрывается сейчас>

## Воспроизведение Регрессии `[опционально]`
- Исходная проблема: <только для исправления бага>
- Как воспроизвести до фикса: <команда, шаги или заметка>
- Что теперь доказывает исправление: <тест или команда>

## Обязательные Проверки

### Автоматические
```sh
<command 1>
<command 2>
```

### Ручные `[опционально]`
- <сценарий 1>
- <сценарий 2>

## Негативные И Граничные Случаи `[опционально]`
- <сценарий ошибки>
- <граница или некорректный ввод>

## Приемка
- [ ] <главная обязательная проверка>
- [ ] <дополнительная обязательная проверка>

## Открытые Риски `[опционально]`
- <известный пробел в проверках>
````

## Правила Адаптации

- Если репозиторий уже использует `TEST_PLAN.md` или иной принятый путь, сохраняй его.
- Если задача только про документацию, низкорисковый рефакторинг или мелкую техническую правку, не создавай отдельный тест-план без явной пользы.
- Если точные команды пока неизвестны, используй временные значения и помечай их как предположения.
- Если этап меняет поведение, соответствующая проверка должна быть определена до закрытия этапа.
